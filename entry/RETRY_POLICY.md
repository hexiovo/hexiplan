# 有进展继续，最多30次；循环或卡死提前停止（对话适配 v1.15）

本规则以最多30次修复覆盖旧两轮/三轮及无固定次数规则，适用于三个消耗档位、无需审核或人工审核、代码修复及工具/流程重试。用户于2026-10-20明确要求：不在同一问题卡死或循环就继续做，陷入循环或卡死就停。原文保存RETRY_PROGRESS_AUTHORIZATION.txt，旧默认无需审核政策仍有效。

## 继续的条件

有新的相关证据、缩小了原因范围、解决了部分关键失败，或明确改变了下一步处理方式且有事实依据，在30次上限内可以继续。正常失败不等于卡死。每次只记必要摘要：处理哪个问题、试了什么、实际结果、新发现、下一步具体改变；引用现有证据，不为了证明进展额外运行重复测试。任务范围/权限仍按原授权处理。

## 停止的条件

同一问题反复执行相同做法、得到相同结果且无新信息；方案A/B来回切换又回到已失败状态；持续尝试没有缩小问题或改善结果；明确缺少权限、资料、服务能力且没有可行新路径；进程实际无进展并经必要状态判断确认卡死。出现这些情况就停止相关重试及依赖动作，说明已尝试的办法、卡点、未完成项，以及需要的新资料、权限或外部条件。不能靠换代理、改问题名、重置次数、升消耗档或重开补充轮继续兜圈。

耗时长不等于卡死，有可信运行进度时合理等待；没有进度时只查看必要状态，不高频轮询、反复启动同一命令或长时间占用鼠标。进程卡死的停止仅针对本任务拥有的操作，不操作无关会话。无需审核不覆盖真实阻塞停止规则。

用户提供新条件或外部状态确有变化后可以重新规划继续，记录新依据与旧停止原因。原始历史保留，不假装旧问题从未失败。成功即结束，不继续测试。

## 状态入口和失败证据

使用entry/workflow_adapter.py，原tools/workflow.py保留。失败verdict证据在原字段外增加repair_assessment：

```json
{
  "issue_id": "同一实际问题的稳定标识",
  "status": "progress",
  "attempt": "本次具体尝试",
  "outcome": "实际结果",
  "reason": "为什么有进展或为什么应停",
  "new_information": "本轮新证据/已缩小的原因/实际改善",
  "next_action": "基于该证据，下一步具体改变什么"
}
```

status只接受progress、stuck、loop。明确stuck/loop立即blocked；progress须有新信息与具体下一步，而且不能重复已有同问题/尝试/结果/信息组合。缺少可判断进展的记录时先停止盲目重试并补齐真实依据，不把猜测写成进展。

适配器将原固定次数分支在内存改为进展判断与30次上限共同生效；当前修复阶段的repair_rounds最多30，同一问题在repair_history中累计获准的修复次数也最多30。取两者较大值判断，不因跨阶段或局部计数重置而获得额外次数，repair_history和repair_stop_reason保留依据。跨代理/档位/补充/恢复复用同一问题的历史，不能手改state.json或伪造新issue_id。PASS仍须满足原证据检查，不要求人为补一份重试记录。

代码仅校验记录及精确归一化重复模式；真实语义进展、隐蔽循环和进程卡死由代理结合状态判断，不能宣传成已验证的通用自动检测器。按项目规模保留最小必要检查，本规则不增加测试规模，也不重跑无关检查。

## 30次上限（用户最新补充）

用户明确要求“设置一个上限吧，30次”，原文保存RETRY_LIMIT_AUTHORIZATION.txt。首次实施不计入修复次数，允许最多30次修复，第30次结果通过就正常结束；第30次仍失败则停止，不启动第31次。循环、卡死或无实质进展仍立即提前停止，30不是必须用满的次数。

同一问题跨代理、档位、恢复和补充累计，不以改名/重规划/清零绕过上限。代码修复阶段计数与同问题历史计数共同约束；普通工具重试也由代理记录次数并遵守30上限，不以反复重启命令规避。到限后说明已做尝试、剩余问题及需要的决定，不默认自行续开30次。
