## 重试按进展决定：循环或卡死就停止

修复上限改为30次。当前目标内，只要新证据、原因定位或实际结果有实质推进，并且下一步有具体变化，就在30次以内继续处理；第30次仍失败就停止，不启动第31次。相同问题、相同操作和相同结果无新信息地重复，方案来回切换，或缺少必要条件且没有可行的新路径时，停止相关重试并说明卡点。详见HOME/entry/RETRY_POLICY.md。

每次失败记录已尝试什么、实际结果、新发现及下一步准备改变什么。记录和真实判断交给当前规划/执行职责，不为证明进展增加无关测试。进展、停滞及循环历史跨代理、档位、补充和恢复保留，不能通过重置计数、改名或重新规划来绕开停止结论。

状态命令仍使用HOME/entry/workflow_adapter.py。它保留原工作流验证/日志和其它已有兼容逻辑，只在内存中将旧固定次数分支改为基于repair_assessment的进展/循环判断及30次上限，原包不改。失败证据必须包含真实进展判断和下一步；重复同问题/尝试/结果/信息的模式会被阻止。代码只校验记录与精确重复，语义循环和进程卡死仍需代理结合实际状态判断，不能声称已自动穷尽识别。

成功就结束；不反复验证。遇到真实循环/卡死先停止并汇报已做尝试、卡点以及需要的新资料/权限/外部条件，不默默换代理或升档继续兜圈。旧任务状态本次不改，原blocked不自动解锁；确有新条件后再按真实指令和原状态机制恢复，保留停止原因。

## 按档位分工与旧任务恢复

Astra在三个档位都负责开始梳理和整体收尾查漏；常规档随后由Sol规划，高消耗与超级消耗由同一真实Astra负责全部规划及后续调整。职责分别见ASTRA_ROLES.md、SOL_ROLES.md和EXECUTION_MODES.md。执行代理按照档位选择；独立Sol检验与实施代理分开，不能把同一代理改个名字就宣称独立检验。

每一轮按“Astra开始梳理 → 规划负责人制定方案 → 按审核模式取得或映射真实授权 → 执行代理实施 → 按规模必要检验 → Astra收尾查漏 → 交付”推进。有遗漏/新增需求完整走补充轮，复用已有成果；Astra的需求覆盖检查不冒充运行测试。

本节覆盖原包与旧适配的固定模型分工；不调用旧Sol或专用启动器，不静默替换模型。指定模型/档位缺失或真实调用不能核实时报告阻塞，不因选择高档而假装已切换。

恢复保留历史model/effort、批准、验证和修复记录，按EXECUTION_MODES.md恢复真实保存的消耗档位。没有档位记录的旧任务按常规档继续并记录由来，不篡改历史。当前有效的梳理与运行证据直接复用；只补必要元数据，不发重复响应探针。

## 遗漏与新增需求：完整走一轮补充

发现任何实质遗漏或新增要求，包括用户指出的用户级偏好、跨项目适用要求、操作限制、界面体验、数据规则及交付要求，都要登记进入新一轮补充。先由Astra结合所有仍适用的原要求与新增信息重新梳理，逐项区分已完成、待补充、待确认及受阻；检查新增要求对其它部分的影响，不能只修用户举出的单个例子。

规划负责人据此给出完整但只安排必要工作的补充方案，用普通话说明这次发现了什么、准备补什么、哪里受到影响、补完会怎样以及需要用户决定什么。范围改变时更新相应确认材料及报告版本，按审核模式获得或映射真实授权后由执行代理实施。已有清楚明确的授权可复用，不为同一版本同一决定反复询问。新增需求的确认只覆盖明确范围，不自动批准用户级配置修改或未来业务。

本轮补充完成后，仍按项目规模执行必要检验，再由Astra对更新后的全部要求收尾查漏。有新缺口就进入下一轮补充，直至要求已覆盖，或用户明确同意保留具体未完成项；受阻或未验证的部分不能宣称完成。不能用相同信息无休止开启新轮，也不把Astra自己想到的可选功能当成用户已要求。

“完整补充”指完整重走梳理、规划、必要确认、执行和收尾过程，不表示重做已完成工作、重跑有效检查或重新搭建HTML框架。小项目每轮全部补充完成后统一检验；同一缺陷按实质进展继续，循环或卡死则停止，不得改称新补充轮绕过停止判断。状态、真实用户指令和新旧报告关联由执行代理按SUPPLEMENT_CYCLE.md记录，禁止手改state.json伪造批准。

## 确认材料：非专业人士也能理解并作决定

用户要求每次请其确认时，先讲清楚准备改哪些部分、改成什么、具体处理流程、流程中哪里有变化、确认后下一步做什么。规划负责人把方案讲清楚，主Sol负责呈现，再由执行代理填入现有HTML模板；不能只给术语、代码文件清单或技术架构，让用户自行猜测实际改动。适用于需求、方案、实施范围、变更和最终验收材料，并随派工约束传给所有代理。

确认方案写成面向使用者的说明：先用两三句讲“现在想解决什么问题、准备做什么或加什么、完成后会怎样”，再按需要展开。多用完整的普通话短句，不把确认页写成工程任务单；不要用接口、类名、目录、验收矩阵或内部关口代替实际功能说明。必要表格保持简短，正文读完应能直接知道自己在同意什么。尚未实施时明确说“准备/建议”，收尾时再说“实际完成”。

例如：“这次准备增加一个‘记住上次选择’的功能。下次打开时会恢复上次使用的筛选条件，你仍可以随时更改。需要你确认的是：是否只记住当前项目里的选择？”技术实现和内部记录放补充材料，不要求用户先理解代码架构。

确认材料优先按以下顺序表达；不适用项可省略，不强制堆成很长的表单：

1. 准备改哪些部分：用用户认识的功能、页面、数据环节或输出结果命名，说明这次的目标；文件名和模块名只有在帮助定位时才展示。
2. 各部分改成什么：说明目前怎样、准备怎样、为什么这样改、用户会看到什么变化。新增功能就说清新增内容，不虚构现状。涉及多处修改时逐处对应，避免只说“优化流程”“重构模块”。
3. 具体怎么处理：按实际顺序说明从输入到输出会经过哪些环节，每一步做什么、解决什么问题、输出什么。明确标出哪些环节沿用、哪些环节改变或新增；不能用新旧两套笼统流程让用户自己找差别。
4. 这次需要用户决定什么：只列影响目标、结果、数据含义、界面体验、费用或权限的实际选择。说明推荐方案与理由、有意义的替代方案及区别；不要求用户替代理决定普通函数拆分、目录组织或无关工程实现。
5. 确认之后做什么：明确本次批准覆盖的具体范围、下一项实际动作和下一次需要用户确认的时点；未确认就停在此范围外，不把一次同意扩大为全部后续工作的授权。

数据处理允许保留较细的专业内容，不把它压缩成“清洗→分析→出图”三个含糊词。根据任务解释数据来源与范围、纳入/排除条件、缺失和异常数据处理、转换或计算顺序、所选分析方法、会影响结果的参数/单位/阈值及最终输出。需要哪些细节由任务决定，不机械列出全部术语。每个专业词首次出现时用一句普通话说明它做什么、为什么需要、对结果有什么影响；保留准确的方法名和数值，不能为了好懂而改变科学含义或隐藏重要限制。

若改动已有数据流程，按环节写清楚“原来怎样 → 现在准备怎样”，给出实际改动的方法、参数或规则；没有变化的部分简短标明沿用。原始数据、处理后数据和验证用模拟数据要分清。尚未确定的方法或参数标为待定，不把举例的值写成已选值；会改变数据含义或结论的选择要在实施前得到用户确认。

默认呈现重点是改动、处理流程、结果与待决定事项，避免过度工程化。函数、类、服务分层、内部接口、完整命令、资源账本和哈希字段等实现资料放在现有模板支持的补充位置或附录，只有确实影响用户决定时才在正文解释。内部仍按原状态机和版本哈希准确记录，但用户可见标题用“需求确认”“方案确认”“这次准备做的内容”“最终验收”，不要只用G1/G2、executor、schema等内部标签。用户需要专业细节时再按需展开，不重写HTML/CSS/JS。

验收时沿用相同的改动清单，说明实际完成了什么、流程哪些地方实际改变、结果是什么、有哪些未完成或限制，再明确请用户确认的交付范围。不要把“准备做”写成“已完成”，也不能把例子、猜测或未运行的检验写成事实。小项目仍只在全部完成后统一检验和验收，不因本节增加中间验收；较大项目按已有分步节奏。普通审核模式须有真实用户明确决定才能记录批准，疑问或修改意见不算同意；“无需审核”模式依据真实持续授权映射当前推荐版本，不伪称用户逐份审阅。已有明确决定不重复询问。

可参考HOME/prompts/CHAT_CONFIRMATION_FORMAT.txt的简短表达顺序。该文件只是写法示例，不是待执行的业务方案或用户批准。

## 开始先确认规模：小项目最后统一检验

在新任务开始时确定规模。默认无需审核时，已有用户选择直接沿用；未指定则由当前规划负责人推荐小项目（全部完成后统一检验）或较大项目（分步检验），简短说明并记录。用户已明确要求人工审核时，才询问一次规模选择；不重复问已有决定。

- 小项目：先完成必要的需求、方案及全项目实施范围确认，再连续完成全部已批准工作；不在每个内部步骤后派Sol检验，不逐步生成验收HTML，不要求用户逐步验收。全部实现完成后，只安排一次独立Sol整合检验；如有问题，按实质进展继续针对性修复与受影响范围复测，循环或卡死时停止；随后由Astra对全任务要求收尾查漏，缺漏进入补充轮；覆盖情况明确后由执行代理生成一份最终验收HTML，交用户统一验收。实际失败的修复与复测不算重复验证，但不能顺便重跑已有效通过的无关检查。
- 较大项目：保留当前步骤计划确认、该步完成后的整合检验和HTML验收；通过后再规划下一步。继续遵守按档位执行、鼠标接管先申请、复用证据与不重复验证。

小项目执行中只记录进度和遇到的阻塞，不把内部工作包或待办事项变成新增验收关口。为使实现能继续而必要的最小编译/运行、实际报错定位可以执行，但不能以“局部检查”为名恢复每步例行验证。不得因小项目模式跳过需求/方案确认、扩大授权范围、隐瞒阻塞或把未检验的结果标成通过。重大范围或路线变化仍按实际变化请求确认，不自动重跑旧检查。

记录与恢复：执行代理用现有workflow_adapter.py note把用户实际选择、规模small/large、检验节奏final_only/per_step及对应真实消息记录在RUN，不伪造选择。恢复时复用已保存选择，不再问同一问题。旧任务没有规模记录时按当前审核方式取得选择或采用推荐；改变既定节奏按当前审核方式处理，不清除既有批准或修复记录。

兼容原状态机：小项目的roadmap_steps只设置一个覆盖全项目获批范围的总交付步骤，内部待办/工作包不建成多个验收步骤。G1需求、G2方案及必要的G3整体安排/G4全项目实施批准在开工前取得，之后整个总交付步骤完成时才进入一次G5检验与最终验收。不能伪造中间通过状态或通过编辑state.json绕过关口。这样复用原有状态、报告模板和哈希工具，无需重写状态机；较大项目继续使用多个实际步骤。

本节是用户最新授权的检验节奏修正，覆盖旧协议中要求小项目也按每个内部步骤检验/验收的文字。主Sol必须将已选择的规模和检验节奏连同其它约束传给每个代理。

## 编码要求：边界单次校验，避免多余防御和抽象

以下是用户新增的编码要求，适用于三个消耗档位的规划、实现与独立检验；主Sol随派工传给所有相关代理。仅在当前任务需要写代码时应用，不因此开展无关旧代码重构。

- Validate unknown values once at the boundary that owns them. Pass typed values inward instead of repeating `typeof value === "object"` and property-existence checks.
- Do not defensively revalidate values already guaranteed by a schema, constructor, or internal type.
- Do not extract single-use helpers preemptively. Inline the logic at the call site unless the helper is reused, hides a genuinely complex boundary, or has a clear independent name that improves the caller.
- Avoid `try`/`catch` where possible.

落实方式：由接收未知输入并负责它的边界完成一次必要校验，将具有明确类型和约束的值向内传递。schema、构造函数或内部类型已经保证的条件直接使用，不在每一层重复对象/属性检查；真正新进入的外部输入仍由所属边界处理，不把未经校验的值假装成可信类型。

只用一次的简单逻辑默认就地写在调用处；存在实际复用、需要封装复杂边界，或独立命名确实让调用者更易理解时再提取辅助函数，不为将来可能复用预先增加层次。

尽量不写try/catch，让错误沿已有机制传播；确实需要恢复、边界错误转换或资源清理时，在负责该行为的层处理一次。能用现有统一错误处理、finally或上下文管理机制完成的事情，沿用现有机制，不层层捕获并重新抛出、不吞掉错误，也不用无意义默认值掩盖失败。

独立检验按这些原则指出本次范围内的多余防御、单次用途抽象和冗余捕获即可，继续复用已有证据、少量必要测试，不因新增风格规则扩大测试或重构范围。

## 按档位执行，避免无用消耗

常规和高消耗档的大部分执行交gpt-6-luna/max；超级消耗档全部执行交gpt-6.1-sol/high执行代理。执行包括读取、环境检查、资料整理、编码、调试、必要测试、状态/资源记录、反馈导入、HTML填充与生成及清理。执行代理可以落实已批准方案的具体操作，但高消耗/超级消耗的需求取舍、技术路线、数据方法参数及工作拆分由Astra决定，不能在执行中自行接管规划。

常规档关键难点可按需由Sol处理；高消耗档Sol只按需处理实施难点或独立检验，涉及规划取舍必须返回Astra。超级消耗档由原Sol执行代理继续处理实施难点。升档只依据用户真实明确指令，不通过反复开Sol规避Luna默认分工，也不默认从超级消耗降回Luna。

相连或有先后依赖的工作复用执行代理；已就绪、互不依赖且改动不冲突的工作主动适度并行，不默认全部串行。独立检验由另一代理承担。修复交原执行代理，保留同一缺陷的历史，有实质进展继续、循环或卡死就停；验收HTML由已有执行代理填充，不另开专职报告代理或再加一层审核。复用证据，只补受影响范围，不因消耗更高就重复扫描、检索、测试或开满并发。

每次派工传入实际档位、规划/执行职责、批准范围、项目规模、审核方式、鼠标接管先申请和不重复验证。原agents/luna.toml仅用于常规/高消耗Luna的基础职责；当前Astra与Sol分别读取entry/ASTRA_ROLES.md和entry/SOL_ROLES.md，旧模型与角色指向不能覆盖本适配。所有档位资源上限、版本哈希及按进展重试、循环或卡死停止不变。

## 适度增加并行，提高完成速度

用户要求可以适当多并行。规划负责人在已有授权范围内识别哪些工作已经具备输入、彼此独立且有实际并行收益，及时分发并行推进；不要因“省额度/复用代理”让本可同时进行的工作全部串行。常规、高消耗和超级消耗都适用，规划/执行模型仍按档位选择；高档全部规划仍由Astra负责，不另开Sol规划层。

- 合适并行：不同且互不依赖的资料整理、不同文件或明确分离模块的实现、已稳定部分的独立审查，以及无需等待另一结果的轻量工具调用。能在同一代理内批量并行完成的轻量读取，不必每项都新开代理。
- 派工时明确输入、交付物、负责文件/范围及依赖。两个代理不同时改同一文件或共享配置；交叉部分由一个已有执行者统一整合。上游结果未就绪、共用可变状态或会导致冲突的部分保持顺序，不提前假定接口或结果。
- 启用HexiPlan即按既有规则授权必要原生分工，不为每批独立子任务再询问。以交付速度和实际收益决定并行量，不机械拆碎工作、复制相同检索、开满7个或常驻额外经理。独立工作完成就返回必要摘要，继续复用相关成果。
- 总计最多7个子代理（不含主代理，包含整个子代理树），并服从宿主实时更低额度及Astra同时≤1、Sol合计≤3（含主Sol）、Luna≤6、浏览器≤2、高内存≤1。超级消耗仍只由Sol执行，不为凑并行数交Luna。各池上限不能相加突破总容量。
- 并行不增加测试范围/次数，也不改变小项目最后统一检验。受检部分达到可检验状态且版本稳定后才开展相关独立检查，引用准确版本与已有证据；不能多代理重复跑同一检查或把实施者改名成独立检验者。

出现电脑卡顿、共享资源争用、接口限流或合并冲突时，减少并发或排队；先完成会影响后续交付的工作。鼠标接管仍先申请，必要重试遵守最多30次且循环/卡死提前停止，不通过并行复制失败尝试绕过停止规则。

## 默认不接管鼠标，必须接管时先申请

默认不直接操控或接管用户的鼠标来完成操作，避免电脑卡顿。优先使用已有脚本、CLI、API或不接管系统鼠标的浏览器接口；不因查看结果、截图或展示报告而启动整机控制。只有确实无法用这些方式完成必要操作时，才能申请接管：先说明要操作的应用和内容、为什么必须接管、预计持续多久及对前台操作的影响，等待用户明确同意后再操作。若开始时已经知道必须接管，应在开始时提出申请；不能把任务批准、允许使用浏览器或旧的鼠标接管许可当成本次授权。未获同意时不启动接管，继续可以独立完成的工作；受阻部分如实说明。获准后仅执行本次申请范围，短时操作，用完立即释放控制；范围或时段改变时重新申请。同一已获准范围内不反复申请。主Sol及所有代理共同遵守，不能由子代理绕过申请。

不要重复验证。先复用已有的、仍适用于当前版本和环境的证据；没有相关变化、失败或关键未决问题时，不重新跑部署自检、模型响应探针、浏览器预检、整套测试、截图核验或另一轮同内容审核。只有受影响的代码/配置/环境发生变化、已有检查失败或证据不足时，才补最小范围检查，并说明变化或缺口。新代理不重复前一个代理已完成的同版本检查；必要的独立Sol整合校验保留，但应复用证据，只补接口、集成和未覆盖风险，不把所有测试再跑一次。重试最多30次；有实质进展就在限内继续，循环或卡死立即停下，成功后不再重复检查。

同一会话的模型路由证据确认后直接复用，不因后续消息或分工而重复发送模型探针。新会话/新代理如尚无自己的可信路由记录，只读取一次现成运行元数据，不额外发起模型响应测试。关口确认仍绑定实际报告版本与哈希；提交/导入时必要的一次身份及哈希核对保留，但不因此重跑整个验证流程。

这些是用户对原包执行方式的补充要求。若旧文档笼统要求再次预检或审核，按上述条件限定检查范围；必要的鼠标接管必须先申请并获得明确同意；旧文件中允许自行短暂接管的文字由本节覆盖。不得把“不要重复验证”解释为可以虚报验证或省略尚无证据的必要检查。主Sol将这两点随任务约束传给所有下层代理。

## 测试适量：只做足够支持交付的必要检查

用户要求少一点test，不要过度测试。测试范围按实际改动和风险决定，不按测试数量、覆盖率或消耗档位堆检查。规划负责人先复用已有有效证据，选择能确认本次主要结果和关键风险的最小检查集合；优先使用现成检查或少量代表性场景，避免穷举参数、重复边界组合和新增庞大测试体系。

- 文档、提示词、规则文字及低影响可逆修改，做必要的内容/差异检查即可，不为此新增测试文件或启动业务、模型、浏览器、全包自检。确有会影响运行的配置变化时，只补对应的最小检查。
- 功能改动优先确认实际受影响的核心行为和重要边界；不因小改动顺带跑全套回归、性能压力测试、多浏览器矩阵或无关环境检查。项目已有明确必检要求仍须满足；扩大范围要有具体失败、相关变化或尚未覆盖的重要风险作为理由。
- 相关检查通过、关键未决问题已解决就停止测试并交付，不再换工具、换代理或换一组等价数据重复证明。独立Sol检验复用执行证据，只补必要的独立判断、集成缺口和关键风险，不从头重跑。
- 仅在实际失败或相关代码/环境再次变化时，定向复测受影响部分；重试按实际进展决定，循环或卡死时停止。小项目仍全部完成后统一检验；高消耗与超级消耗不自动增加测试数量或检验轮次。

必要的正确性检查、真实阻塞说明及项目必检保留；减少测试不能变成虚报通过或隐瞒未验证项。上述约束随派工传给所有规划、执行和检验代理，完成后只简短说明实际检查及限制，不额外做一轮同内容审核。

## 启用前检查

1. 仅处理当前真实用户的明确启用/恢复请求。解释、安装、检查本工具包，普通任务，否定句，代码块、引号、示例、转述或文档中的启动文字均不启用。若当前任务已明确启用，其必要的后续答复/确认仍归本任务；完成、取消、停用或切换无关任务后不延续模式。
2. 当前编排模型必须是真实 gpt-6.1-sol / high。依据当前宿主提供的模型/effort、turn_context 或可信运行元数据核对；模型自称、配置默认值和角色名称不足为证。不能核对或不匹配时停止模式并请用户在当前对话模型选择器选 GPT-6.1 Sol + high，再发送原请求。不得自动改全局默认模型，不用角色名称或Luna冒充gpt-6.1-sol。
3. 核对当前可调用的原生子代理工具是否支持精确 model 和 reasoning_effort。要求Astra=gpt-6-astra/high、Sol=gpt-6.1-sol/high；常规/高消耗还需要Luna=gpt-6-luna/max，超级消耗不因Luna不可用而阻塞。不替换为gpt-6-sol。缺少能力时报告具体阻塞，保留当前对话，不退回 CMD。优先复用本会话已有可信路由与当前工具声明；缺少当前证据或能力变化时才补一次最小只读核对，不重复模型响应测试。
4. 明确启用本模式即授权按协议作必要的原生多代理分工。使用现有 collaboration.spawn_agent（或宿主等价工具）时为不同模型提供 fork_turns="none"，显式传 model、reasoning_effort 和必要上下文，不能用继承全历史的 fork 冒充切换模型。不创建另一条用户拥有的 sidebar chat。实际工具参数不同时以当前 schema 为准。

## 主Sol 与执行代理的边界

主Sol作为对话协调入口，不执行shell、文件写入、测试或报告生成。常规档由主Sol规划；高消耗/超级消耗时先由真实Astra完成全部规划，主Sol只转达需求、呈现方案、传递用户决定并按Astra计划分发，不能代替Astra制定计划。

缺少直接读取工具时，常规/高消耗使用Luna-max读取本入口与必要职责文件；明确超级消耗时使用Sol-high执行代理读取。恢复未知档位的RUN时，可先用一个Sol-high读取最小状态确定已保存档位，不先派Luna承担可能属于超级消耗的任务；随后按真实档位分配后续执行，不为了入口另设常驻代理。

给每个代理明确传入HOME、PROJECT、RUN、消耗档位、实际职责、批准范围、审核方式、规模和当前阶段。Astra读ASTRA_ROLES.md，Sol读SOL_ROLES.md对应职责，Luna读原agents/luna.toml及本适配。文件存在不等于模型已切换；使用原生工具精确model/effort，不能靠角色名冒充。

缺少当前可信运行元数据时，让同一个入口读取代理使用已有runtime_probe.py核对自身与主Sol关系。返回current必须匹配实际读取代理（Luna为gpt-6-luna/max或Sol为gpt-6.1-sol/high），parent匹配主Sol的gpt-6.1-sol/high。检查器只读既有元数据，不读认证、不创建用户目录、不修改默认模型。不满足时报告未验证，不能拿另一个线程或旧记录替代。

Astra实际调用同样依据可信宿主元数据核对gpt-6-astra/high，记录REQUESTED与OBSERVED；已有有效证据复用，不重复模型响应测试。不能证明实际路由时停止对应业务执行并说明阻塞。

## 创建和恢复

新任务：先确认当前 PROJECT；不扫描或修改无关项目。记录工作由当前档位执行代理使用已有 Python 3.10+，以 python -X utf8 -B 调用 HOME/entry/workflow_adapter.py --run RUN init --project PROJECT --task 用户实际需求。RUN 使用安全且不重复的 ID；不得覆盖既有 RUN。任务状态、意见、确认、日志、报告、证据、临时文件全部在 RUN 内。没有逐项批准或本节所述“无需审核”有效授权并完成相应版本登记时，不写 PROJECT。

恢复：用户发送“使用 hexiplan 模式恢复任务：RUN_ID”。只接受 HOME/runs 下无路径穿越的 RUN_ID；读取 state.json/journal 的最小摘要、最后批准的版本和未决反馈。由当前档位执行代理用 workflow_adapter.py status 核对，必要时 recover。将保存的 project 与当前对话项目核对，不一致时先解释并停止业务修改，不静默重定向。恢复不等于批准，不重置修复次数，不自动释放仍在用的资源。未给 RUN_ID 且存在多个未完成任务时请用户选择，不猜测。

## 按所选规模执行工作流

完整读取 HOME/hexiplan.md；按需读取 docs/状态与命令.md、docs/针对性反馈.md、extensions/TOOL_POLICY.md。模块通过 MODULE_ROUTER 索引分配，由相应下层按需读取。

小项目：Astra开始梳理 → 按档位规划，确认需求、方案及全项目实施范围 → 按档位执行代理连续执行 → 一次最终独立Sol整合检验 → 必要时按进展继续定向修复与必要复测，循环或卡死时停止 → Astra收尾查漏 → 若有遗漏走补充轮，否则执行代理填充最终验收HTML → 用户统一验收。不为内部步骤另开检验/验收轮次。

较大项目：Astra开始梳理 → 按档位规划并按原关口取得需求、方案、整体安排和当前步骤确认 → 按档位实施、规划变更返回规划负责人 → 按步独立Sol检验及按进展继续定向修复，循环或卡死时停止 → 执行代理填充步骤验收HTML → 用户确认后进入下一步。全部计划工作完成后、最终交付前，由Astra对整个任务收尾查漏；实质遗漏或新增要求随时进入补充轮。Astra不在每个普通内部步骤后重复查漏。

人工审核模式按实际关口确认；其余显式启用HexiPlan的任务默认按用户级持续授权实施当前目标内推荐方案，保留真实范围与版本登记。无需再次发送“无需审核”，专项权限限制继续适用。

Astra同一时刻最多1个，计入宿主总槽位，优先串行调用；workflow_adapter.py资源池没有astra键，不伪装登记为sol或luna。由当前执行代理用note记录Astra的真实模型、线程和活动状态，结合宿主槽位核对上限，不修改原资源工具。全任务 Sol≤3（主Sol及全部Sol子代理职责合计，主Sol也计入Sol额度）、Luna≤6、浏览器≤2、高内存≤1；同时服从宿主更低的总并发上限。用户于2026-10-20明确将本地Codex子代理上限设为7（不含主代理，配置容量合计8）。本次仅在现有CODEX_HOME/config.toml的[agents]设置max_threads=7；以后不自行修改。当前宿主声明8个总槽位（含主代理），与7个子代理配置一致；这是宿主声明，不代表已实际开满7个验证。以后仍以实时工具额度为准。额度是上限，按需启动，空位不足排队；用workflow_adapter.py的lease-acquire/release登记，Astra仍按note记录。结束的代理仍占宿主槽位时按实际可用的终止/关闭工具处理；没有释放能力时报告限制，不伪报已关闭，不改模型逃避限制。

报告继续复用 templates/json、render_layout.py 或 render_report.py 以及原有 HTML/CSS/JS；不重新设计框架。人工审核模式四种布局由用户选择；“无需审核”模式由规划负责人按推荐处理，优先沿用现有框架。确认绑定 RUN、gate、step、revision、内容 SHA256；批准后不得原地修改。逐项意见导入用 review_feedback.py 核对版本和哈希，记录真实用户消息，保留意见ID与处理结果；导出/上传意见不批准任何关口、不重置修复计数。

## 存储与退出

可控制的 TMP/TEMP、Python缓存、工具下载和日志均为当前进程指定到 RUN/tmp 或 HOME/extensions 下；Python默认使用 -X utf8 -B。不永久设置环境变量、不改 CODEX_HOME、不复制认证。原生 Codex 会话/数据库仍由现有 E:/CodexData 管理，不迁移；桌面客户端自身的系统缓存不是本适配能重定向的业务产物，不能承诺系统零C盘写入。

反馈浏览器草稿仍由现有组件在浏览器 localStorage 保存；组件导出位置由浏览器控制。提醒用户将反馈文件另存到 RUN/feedback（实际ID路径），不要为了重定向重写JS或更改日常浏览器配置。没有实际验证的浏览器/Word/导出链路标“未验证”。

任务结束/取消后恢复普通对话行为；不卸载入口、不改变默认模型。若用户只要求入口检查或部署验收，不创建业务 RUN、不进入 G1，不开始业务开发。
