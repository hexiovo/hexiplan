# 对话调用与恢复

## 直接开始

在正常打开的 Codex 当前对话中发送（用实际需求替换第二行）：

```text
使用 hexiplan 模式完成以下任务：
这里填写我的需求。
```

入口固定在 H:/AIcode/HexiPlan，无需每次填写工具包路径，无需双击CMD，无需逐项目登记。只有明确启用的当前任务才使用 HexiPlan。普通请求、介绍、否定和引用示例不启用。

启用HexiPlan后，未注明消耗档位就按常规模式使用；开始和收尾均由Astra-high思考。规划与执行按下表分配。当前对话继续使用GPT-6.1 Sol/high作为协调入口，高档规划由真实Astra代理完成，不需要来回手动切换模型或改变全局默认模型。

启用后默认无需审核，按推荐方案连续执行和记录，你不必再逐项确认。项目规模已说明就沿用，未说明则推荐并简短解释；只有你明确要求人工审核时才按关口等待决定。

## 三种消耗模式

| 模式 | 规划 | 执行 |
| --- | --- | --- |
| 常规模式（默认） | 6.1 Sol-high | Luna-max优先 |
| 高消耗模式（明确指定） | 全部交Astra-high | Luna-max优先 |
| 超级消耗模式（明确指定） | 全部交Astra-high | 全部交6.1 Sol-high |

Astra在三档都负责开始梳理与整体收尾查漏。高档全部规划包括最初方案、步骤、数据方法、推荐选择和后续补充，不只让Astra看一遍Sol计划。超级消耗的记录、报告、固定HTML填充也由Sol执行代理完成；独立检验仍由另一名未实施的Sol承担。

开始时仍用原启动句，在需求里加档位即可，例如：

```text
使用 hexiplan 模式完成以下任务：
高消耗模式。这里填写我的需求。
```

超级档将上例改为“超级消耗模式”；不写档位即常规。任务进行中可说“切换到高消耗模式”“切换到超级消耗模式”或“切回常规模式”。只影响后续分工，保留已完成工作。恢复同一任务沿用保存档位，新任务默认常规。

只需写“高消耗模式”或“超级消耗模式”；三档都默认无需审核，也仍接受显式“无需审核”。审核方式、项目规模和消耗档位相互独立；不会因为无需审核、任务复杂或检验失败自动升档。讨论、引用示例及否定语句不会切换档位，普通未启用HexiPlan的任务不受影响。

## 默认无需审核

三种消耗档位都默认按推荐方案执行，无需额外写“无需审核”。任务目标内的方案、步骤和后续补充会连续推进，保留简短说明、版本和结果记录。

说“恢复审核”或“后面先让我确认”即可让当前任务重新等待你的决定；说“无需审核”可以切回。恢复同一任务沿用最近的明确选择，新任务默认无需审核。

Astra首尾查漏、必要检验和小项目全部完成后统一检验继续保留；同一缺陷最多三轮修复，成功即止，第三轮仍失败就说明阻塞。鼠标接管仍需单独申请；必要权限或资料缺失时只询问该阻塞。

## 项目规模与检验节奏

已有规模选择直接沿用；未指定时默认采用推荐规模并说明。你明确要求人工审核时，才问一次规模选择。保存记录，恢复时不重复问。

- 小项目：需求、方案及全项目实施范围确认后连续完成，内部步骤不分别检验、不分别验收；全部完成后统一检验，必要时定向修复，最后提交一份HTML让你验收。
- 较大项目：保留分步计划、检验和验收。

小项目在原状态机中记录为一个全项目总交付步骤，不伪造中间验收、不改状态机或报告框架。执行中遇到实际报错可做必要的最小定位，不重新引入每步例行检查。按档位执行、鼠标接管先申请、不重复验证和最多三轮修复继续适用。

## 按档位分工与额度控制

常规/高消耗以Luna执行为主，超级消耗由Sol执行；高档全部规划由Astra负责，主Sol只协调呈现和派工，不重复作计划。优先复用代理与有效证据，按需并行，不开满额度、不因为高档而重复检索或测试。

Sol总额≤3，包括主Sol、执行者与独立检验者；Astra同时≤1，Luna≤6，并服从宿主更低总槽位。无空位时排队，不修改全局并发。原三轮修复、鼠标接管先申请和所选项目规模的检验节奏保留。

## 发现遗漏或又有新要求时

每一轮都先由Astra把要做的事想清楚，再由当前档位的规划负责人制定方案；工作结束后，Astra对照要求检查哪些完成、哪些还没有做到。你后来提出的用户级需求、使用习惯、跨项目要求或其它遗漏，也会连同原要求一起完整梳理，开始新一轮补充，不只是补一句说明。

补充方案会清楚说：这次漏了什么或增加了什么、准备补在哪里、补完会怎样、需要你决定什么。按审核模式处理后由当前档位的执行代理实施，再做必要检验和Astra收尾查漏。完成且仍有效的工作与检查保留，不从头重做；同一缺陷的修复上限不因补充轮次重置。只有需求已覆盖或你明确接受具体未完成项，才说明本轮结束。

用户级要求会明确是本任务要求还是跨项目长期规则；不会把一次项目需求直接扩成所有项目的全局设置。

## 默认不接管鼠标，必须接管时先申请

默认不直接操控你的鼠标，优先用不会接管系统鼠标的方式完成工作。如果确实必须接管，会先说明要操作什么、为什么需要、预计多久以及对前台操作的影响，等你明确同意后才开始；知道需要时在一开始提出。只执行获准范围，用完立即释放；范围或时段改变会重新申请。同一获准范围内不重复申请。任务批准或允许使用浏览器不等于允许接管鼠标，所有代理都遵守这一要求。

已有、仍有效的验证结果直接复用；没有相关变化或失败就不再跑。确有变化或缺口，只补受影响的最小检查，不反复做模型测试、浏览器预检或全套验证。

## 恢复

```text
使用 hexiplan 模式恢复任务：
实际 RUN_ID
```

RUN_ID 是先前任务保存于 H:/AIcode/HexiPlan/runs 下的目录名，不是当前聊天ID。部署没有创建业务RUN，因此现在没有可恢复的业务任务。

恢复读取日志与状态，核对保存的项目及待确认报告版本/哈希。不要把换对话、重启或导入反馈视为批准，也不能因此重置三轮修复边界。项目不一致时先说明，不能静默改到另一个项目。

## 每次确认会说明什么

方案先用说明性的短句讲清“现在想做什么、想加什么、为什么需要、完成后会是什么样”，再展开必要细节。例如：“准备让系统记住当前项目的筛选条件，下次打开可以接着用，你也能随时更改。”不需要你先看懂接口、目录或技术架构。

请你确认之前，会按容易理解的顺序说明：

1. 准备改哪些部分。
2. 每一部分现在怎样，准备改成什么，为什么这样改。
3. 具体流程是什么，哪些环节沿用，哪些环节有改动。
4. 这次需要你决定什么，推荐方案和有意义的选择有什么区别。
5. 你确认后，下一步具体做什么，本次确认覆盖到哪里。

数据处理会保留必要的方法、参数和处理顺序，并解释用途与影响；不会只用“清洗、分析、输出”带过。内部代码组织等工程细节只在影响决定或你想了解时展开。验收时说明实际完成的变化、结果和限制。小项目最终统一验收，较大项目按已选节奏执行。

## 固定HTML确认框架

后续确认材料只填内容，沿用已经写好的结构、样式和反馈界面，不为每个任务重新构建页面。当前档位执行代理填写entry/confirmation/content-template.json中的修改内容、具体流程、数据方法、待决定事项及确认后的动作，再调用固定fill_confirmation.py生成本任务的新版本报告。验收时补充实际完成情况与限制；无关栏目简述或省略空表。

- 空白框架：H:/AIcode/HexiPlan/entry/confirmation/frame/report.html
- 填写示例：H:/AIcode/HexiPlan/entry/confirmation/example/report.html
- 填充说明：H:/AIcode/HexiPlan/entry/confirmation/FILL_GUIDE.md

预览与示例不能批准真实任务。新版本保留旧版本，逐项意见、导出、内容哈希及真实确认记录沿用原流程。无需改全局配置或重启客户端；实际浏览器呈现和导出链路本次未验证。

## 确认和逐项意见

报告继续使用原有模板与界面。用户在HTML里阅读、填写和导出意见，将真正的确认文字/反馈JSON交回当前对话。反馈导出不是授权，导入前核对版本和SHA256；旧报告保留，新修改生成新版本。

浏览器下载位置仍由浏览器控制。请把导出的反馈另存到当前 RUN/feedback；浏览器草稿仍在原组件的 localStorage 内，未迁移浏览器档案。报告里的示例/预览不能批准真实任务。
